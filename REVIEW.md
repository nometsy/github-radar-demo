# GitHub Radar — ревью проекта и план улучшений

**Дата:** 20 октября 2026  
**Версия:** 1.0.0  
**Статус:** рабочее приложение, код в приватном репозитории, CI зелёный

---

## 1. Что работает хорошо

### Архитектура и код

✅ **Честность данных** — главное преимущество: рост звёзд считается только по снимкам, никаких выдуманных оценок. Если пары snapshot нет, UI пишет "insufficient data", а не врёт.

✅ **Separation of concerns** — серверный GitHub-клиент (кэш, retries, rate limit, stale fallback), слой service, валидация Zod, нормализаторы сырых типов, отдельные file/Prisma store.

✅ **Прогрессивный стек** — Next.js 16, React 19, TypeScript 5.9, Tailwind 4, TanStack Query, Motion, Recharts. Всё актуально и документировано.

✅ **Responsive и mobile-first** — нижняя навигация для телефонов (<1024px), `safe-area-inset` для вырезов, 36px tap-targets, убран серый флеш тапа.

✅ **Документация** — README на 240 строк описывает установку, API, снимки, cron, ограничения GitHub API и почему "старые" репозитории в ленте. `docs/ROADMAP.md` раскладывает ограничения GitHub и предлагает приоритизированный бэклог.

✅ **CI** — `.github/workflows/ci.yml` прогоняет typecheck → test → lint → build при каждом пуше.

✅ **Безопасность** — токен хранится только в `.env.local` (серверный), `.gitignore` закрывает секреты, аудит подтвердил отсутствие утечек в коммите.

✅ **Unit-тесты** — 29 проверок построителей запросов, growth-математики, персистентного кэша, спарклайна и localStorage; локальный seed-скрипт для проверки 24h-роста без ожидания суток.

### UX

✅ **RSS-фида** — `/api/radar/feed?lens=new&window=24` возвращает XML-ленту для подписки через ридер.

✅ **Keyboard shortcuts** — `/` фокусирует поиск, `g+d/f/t/a/s/w/c` переключает разделы.

✅ **Empty/error/loading states** — каждая страница обрабатывает пустое состояние, rate limit, сетевые ошибки.

✅ **Watchlist + коллекции** — локальное хранилище (localStorage), export JSON, снимки для сохранённых репозиториев.

✅ **Compare** — до 4 репозиториев side-by-side с измеренным ростом и живыми метриками.

✅ **Leaderboard** — топ-6 измеренных 24h-муверов прямо на Dashboard.

## 2. Что надо улучшить (приоритеты)

### 🔴 P0 — критичные для usability

#### 2.1. Спарклайн истории на карточке репозитория

**Проблема:** рост виден только текстовым бейджем `+500 ⬆ 2.4%` — визуально «плоско».

**Решение:** добавить мини-график 24–48px высотой по точкам snapshot прямо в карточку. Recharts `ResponsiveContainer` + `LineChart` с 2–3 линиями, полупрозрачный градиент под кривой.

**Сложность:** низкая (~1 час); данные уже есть в `history.points`.

---

#### 2.2. Персистентный кэш GitHub-ответов на диск

**Проблема:** сейчас кэш живёт только в памяти `globalThis.__githubRadarCache`. После перезапуска процесса (например, после `npm run build` или reboot) приложение снова тратит квоту на те же запросы.

**Решение:** писать кэш в `.data/cache.json` (аналогично `radar.json`) с TTL и отметкой времени. При старте загружать валидные записи в память.

**Сложность:** средняя (~2 часа): обёртка над `fs.writeFile` + `fs.readFile`, проверка TTL при загрузке.

**Польза:** экономия квоты 30–50% при частых перезапусках разработки; для production — переживание restart без потери кэша.

---

#### 2.3. «New · 24H» — кликабельный счётчик с подсказкой

**Статус:** ✅ уже сделан (ведёт на `/fresh?window=24`), но можно улучшить UX:

- Добавить тултип «All repos created today · click to see filtered by ≥10 stars».
- Рядом с числом показать маленький треугольник `▸` — визуальный намёк на кликабельность.

**Сложность:** тривиальная (10 мин).

---

#### 2.4. Возраст репозитория крупнее и заметнее

**Проблема:** «Created 3h ago» в карточке есть, но мелким серым текстом — пользователь не видит и спрашивает «почему все старые».

**Решение:**
- Если репозиторий создан <7 дней назад, показывать возраст крупным зелёным бейджем **сразу под названием** (`3 hours old`, `2 days old`).
- Для остальных — оставить серой датой.

**Сложность:** низкая (~30 мин); функция `formatRelativeTime` уже есть, надо изменить размещение в карточке.

---

### 🟠 P1 — заметные функции

#### 2.5. PWA (Progressive Web App)

**Проблема:** приложение открывается только по ссылке, не устанавливается на телефон.

**Решение:** добавить `manifest.json` (name, short_name, icons 192/512, start_url, display: standalone), service worker для офлайн-оболочки, `<link rel="manifest">` в `layout.tsx`.

**Сложность:** средняя (~3 часа); нужны иконки в нескольких размерах, базовый SW.

**Польза:** установка на home screen телефона, запуск как «родное» приложение, офлайн-скелет UI.

---

#### 2.6. Web Push уведомления о росте watchlist

**Проблема:** нет способа узнать, что репозиторий из watchlist вырос на N звёзд, кроме ручного открытия приложения.

**Решение:**
- В watchlist добавить порог уведомлений для каждого репозитория (например, «уведомить, если +100 звёзд за сутки»).
- Cron-задача сравнивает новый snapshot с предыдущим; если превышен порог, отправляет Web Push (нужен VAPID-ключ).
- Альтернатива: email через nodemailer (проще, но требует SMTP).

**Сложность:** высокая (~6 часов): регистрация VAPID, подписка браузера, хранение subscription, отправка уведомлений.

**Польза:** высокая для power users, но требует HTTPS.

---

#### 2.7. Радар тем (Topics Radar)

**Идея:** показать, какие **topics** набрали больше всего репозиториев за 24 часа.

**Реализация:**
- Запрос `topic:react created:>=<24h ago>` → `total_count`;
- Повторить для 20–30 популярных тем (ai, rust, typescript, react, nextjs, llm, devtools, cli и т.д.);
- Построить таблицу «topic → +N новых репо за сутки»;
- Кэш 30 минут, подпись «snapshot at HH:MM UTC».

**Сложность:** средняя (~2 часа); 30 запросов = 1 search/min, вписывается в квоту.

**Польза:** показывает, «что сейчас в моде», дополняет AI Discovery и Trending.

---

#### 2.8. Saved Searches (избранные фильтры)

**Проблема:** если пользователь часто ищет «rust cli created:<7d stars:>50», ему каждый раз надо заново ставить фильтры.

**Решение:**
- Кнопка «Save search» сохраняет текущий набор фильтров в `localStorage` с именем.
- В `/search` выпадающий список сохранённых поисков → клик восстанавливает фильтры.

**Сложность:** низкая (~1 час); аналогично watchlist, но проще (нет коллекций).

---

#### 2.9. OG-картинки для шаринга

**Проблема:** ссылка на репозиторий в соцсетях показывает дефолтную иконку Next.js.

**Решение:** `next/og` `ImageResponse` генерирует картинку 1200×630 с названием репозитория, звёздами, языком, ростом и неоновой радарной рамкой.

**Сложность:** средняя (~2 часа); отдельный route `/api/og/repo/[owner]/[name]`, `<meta property="og:image">` в `layout`.

---

#### 2.10. Тема по системе (enableSystem)

**Проблема:** тема фиксирована (dark по умолчанию); у пользователя может быть светлая ОС.

**Решение:** `next-themes` уже умеет `enableSystem: true` — надо только включить.

**Сложность:** тривиальная (5 минут); одна строка в `app-providers.tsx`.

---

### 🟡 P2 — качество и инфраструктура

#### 2.11. E2E-тесты (Playwright)

**Проблема:** сейчас только unit-тесты — нет проверки сценариев «открыть дашборд → добавить в watchlist → собрать снимок → увидеть рост».

**Решение:** Playwright тесты: запуск `npm run build && npm start`, проверка основных потоков.

**Сложность:** средняя (~4 часа).

---

#### 2.12. Метрики и логирование

**Проблема:** непонятно, сколько запросов ушло в GitHub, сколько раз сработал stale-cache, хватает ли квоты.

**Решение:**
- Счётчики в памяти: `cache_hits`, `cache_misses`, `stale_hits`, `github_requests`, `rate_limit_429`.
- Route `/api/metrics` возвращает JSON.
- Опционально: экспорт в Prometheus формате для мониторинга.

**Сложность:** низкая (~1 час).

---

#### 2.13. Планировщик, учитывающий квоту

**Проблема:** cron-задача запускается вслепую, даже если квота исчерпана.

**Решение:** перед сбором снимков проверить `GET /api/system` → `rateLimit.search.remaining`. Если < 5, отложить запуск на 15 минут.

**Сложность:** низкая (~30 мин); обёртка над cron-скриптом.

---

#### 2.14. Кэш в SQLite вместо JSON

**Проблема:** при больших объёмах (тысячи снимков) JSON-файл растёт до 1–2 МБ, парсится за 10–20 мс. SQLite был бы быстрее и проще для миграций.

**Решение:** `better-sqlite3` для кэша, таблица `cache(key, value, ttl, created_at)`.

**Сложность:** средняя (~3 часа).

**Польза:** актуальна при 5000+ репозиториев в snapshot store.

---

#### 2.15. Роли и авторизация

**Проблема:** приложение задумано как личный инструмент; если станет публичным сервисом, нужна авторизация и разделение watchlist по пользователям.

**Решение:** NextAuth / Auth.js + GitHub OAuth, таблица `users`, `watchlist.user_id`.

**Сложность:** высокая (~8 часов).

**Польза:** актуальна только для публичного хостинга.

## 3. Дизайн — что улучшить

### 3.1. Цветовая палитра: добавить третий акцент

**Сейчас:** primary (`#00ff9c` зелёный), cyan (`#00d9ff` голубой), warning (`#ffcc66` жёлтый), violet (`#9b8cff` фиолетовый).

**Проблема:** фиолетовый почти не используется; warning — только для ошибок.

**Предложение:**
- Добавить **розовый акцент** (`#ff6b9a`) для «горячих» проектов (high momentum, топ trending) — визуально отличит их от «стабильно растущих» (зелёных).
- Использовать gradient `primary → pink` для самых горячих карточек.

**Сложность:** низкая (~30 мин); уже есть `--chart-5: #ff6b9a`, надо применить в UI.

---

### 3.2. Анимации: micro-interactions на карточках

**Сейчас:** страницы используют Motion fade-in при переключении, карточки — статичные.

**Предложение:**
- Hover на карточке: лёгкий scale(1.015), тень с неоновым glow.
- Клик на кнопку «Add to watchlist»: пульсация иконки звезды.
- Счётчик «+500 ⬆» при изменении: короткий scale bounce.

**Сложность:** низкая (~1 час); используем Motion `useSpring` и CSS `transition`.

---

### 3.3. Типографика: heading sizes на мобильных

**Проблема:** на телефонах h1 (`text-2xl` → 24px) читается комфортно, но на десктопе выглядит мелковато.

**Решение:** fluid type scale через `clamp()`:

```css
h1 {
  font-size: clamp(1.75rem, 4vw, 2.5rem);
}
```

**Сложность:** тривиальная (15 мин).

---

### 3.4. Spacing: увеличить вертикальные отступы между секциями

**Сейчас:** `space-y-6` (24px) между панелями — для насыщенного дашборда нормально, но при скролле разделы «слипаются».

**Предложение:** на десктопе увеличить до `space-y-10` (40px), на мобильных оставить 24px.

**Сложность:** тривиальная (10 мин).

---

### 3.5. Dark mode: глубже фон для читаемости

**Сейчас:** `--background: #080b10` (L ~3%), `--card: #111821` (L ~6%).

**Проблема:** на OLED-экранах text-on-background контраст 16:1 (отлично), но на IPS выглядит «сероватым».

**Предложение:** добавить вариант «true black» для OLED:

```css
@media (prefers-contrast: more) {
  :root {
    --background: #000000;
    --card: #0a0d12;
  }
}
```

**Сложность:** тривиальная (10 мин).

## 4. Что **не** стоит делать

❌ **AI-описания репозиториев** — выдуманные тексты смешаются с реальными данными и подорвут доверие.

❌ **Синхронизация watchlist с сервером** под видом «облачного списка» — это локальное хранилище, честнее так и писать.

❌ **Оценка роста по возрасту репозитория** (звёзды/день) как «измеренный рост» — это противоречит главной идее приложения. Hidden Gems использует эту оценку для сортировки, но явно подписывает.

❌ **Тяжёлые зависимости** (дашборд-фреймворки типа Recharts Pro, ORM для JSON) — на 4 ГБ RAM сборка уже занимает 4–5 минут.

❌ **Фейковые live-обновления через WebSocket** — данные обновляются с кэшем 3 минуты, имитация «реального времени» будет обманом.

## 6. Итоговая оценка

| Критерий | Оценка | Комментарий |
|---|---|---|
| **Архитектура** | 9/10 | Чистое разделение слоёв, честные данные, прогрессивный стек. |
| **UX** | 8/10 | Отличная mobile-адаптация, честные empty states, но не хватает спарклайнов и PWA. |
| **Производительность** | 8/10 | Кэш, stale fallback, Turbopack — быстро; персистентный кэш добавит ещё +1. |
| **Документация** | 9/10 | Подробный README, ROADMAP, объяснение ограничений GitHub API. |
| **Дизайн** | 8/10 | Неоновая киберпанк-палитра выглядит круто, но нужны спарклайны и больше анимаций. |
| **Безопасность** | 9/10 | Токен на сервере, аудит чист, `.gitignore` корректен, CRON_SECRET для production. |

**Итого:** **8.5/10** — отличный MVP с честными данными и продуманной архитектурой. Главные gap'ы: PWA, спарклайны истории, персистентный кэш.
