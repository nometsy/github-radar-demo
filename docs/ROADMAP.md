# Анализ: что ещё можно добавить и улучшить

Документ описывает реальные ограничения GitHub API (они определяют, что возможно),
а затем — приоритизированный список доработок с оценкой сложности.

## 1. Ограничения, которые задают рамки

| Ограничение | Следствие |
| --- | --- |
| Search API не сортирует по `created` | «Самые новые» нельзя получить напрямую: доступны только `stars`, `forks`, `updated`. Решение — короткое окно (`created:>=`) + локальная сортировка. |
| Поиск отдаёт максимум 1000 результатов на запрос | Пагинация глубже ~50 страниц недоступна, счётчики — приблизительные. |
| Аноним: 60 core/час, 10 search/мин. С токеном: 5000/час, 30 search/мин | Каждая новая «полоса» — это запрос. Агрегации по десяткам тем могут съесть квоту: нужен кэш на 30–60 минут. |
| Growth API отдаёт только `total_count` | «Сколько репо создано сегодня» = один дешёвый запрос `created:>=<00:00 UTC>` без сортировки. |
| Events API — только последние 300 событий, окно ~90 дней | «Кто сейчас коммитит» возможно, но это не полная картина. |
| Снапшоты звёзд живут только в нашем хранилище | Рост всегда отстаёт на часы — это осознанный компромисс в пользу честности данных. |

## 2. Приоритет P0 — быстрые улучшения с заметным эффектом

1. **Возраст репозитория в карточке** (`создан 3 ч назад` вместо даты) — снимает главное непонимание «почему тут старые». *Сделано.*
2. **Короткие окна 6H/12H** и линза «New» — единственный способ показать по-настоящему свежие проекты. *Сделано.*
3. **Кликабельный счётчик «New · 24H»** и честная сноска про сортировку по звёздам. *Сделано.*
4. **RSS-фида линз** (`/api/radar/feed`) — подписка из ридера без открытия приложения. *Сделано.*
5. **Персистентный кэш GitHub-ответов на диск** — переживает перезапуск процесса и не тратит квоту повторно. *Сделано:* `.data/github-cache.json`, атомарная запись, лимиты 200 записей / ~8 MB; относительные окна поиска выровнены по 5-минутным корзинам, чтобы одинаковый запрос попадал в кэш.
6. **Спарклайн истории на карточке** репозитория (по снимкам) вместо только текстового бейджа — рост виден прямо в ленте. *Сделано:* последние 10 дней, до 32 реальных точек; при одной точке линия не рисуется.

## 3. Приоритет P1 — новые возможности

7. **Радар тем** — «какие темы набирают репозитории за 24 ч». Считается несколькими запросами с кэшем 30 минут; честно подписывается, что это снимок, а не поток.
8. **Порог роста + оповещения** — «сообщи, если репозиторий из watchlist прибавил ≥N звёзд за сутки». Реализуется либо cron-письмом, либо Web Push (нужен HTTPS и ключи VAPID).
9. **Сравнение «тогда и сейчас»** — снимки уже хранятся, но в UI нет режима «показать, как репозиторий выглядел N дней назад».
10. **Карточка для соцсетей** — генерация OG-картинки репозитория через `ImageResponse`, чтобы делиться находками ссылкой.
11. **Избранные фильтры (saved searches)** — наборы фильтров с именем, хранятся в `localStorage` рядом с watchlist.
12. **PWA** — установка на телефон, офлайн-оболочка, иконки. Сейчас приложение открывается только по ссылке.
13. **Тема по системе** — сейчас тема фиксирована (тёмная по умолчанию). `next-themes` умеет `enableSystem`; полезно, если пользователь переключает тему ОС.

## 4. Приоритет P2 — качество и инфраструктура

14. **E2E-тесты (Playwright)** — сейчас только юнит-тесты: 29 проверок построителей запросов, growth-математики, кэша, спарклайна и localStorage. Сценарии «создать watchlist → собрать снимок → увидеть рост» не покрыты.
15. **CI (GitHub Actions)** — `typecheck → test → lint → build` на каждом пуше. *Сделано.*
16. **Планировщик, уважающий квоту** — не запускать сбор снимков, если лимит поиска исчерпан; сейчас проверка идёт по факту 429.
17. **Метрики** — счётчики попаданий в кэш, сколько раз сработал stale-фолбэк, сколько запросов ушло в GitHub. Нужны, чтобы понимать, хватает ли квоты.
18. **Кэш ответов в SQLite** вместо JSON — быстрее при больших объёмах снимков и проще миграции. Сейчас JSON-файл прост и достаточен для тысяч репозиториев.
19. **Роли и доступ** — приложение считается личным инструментом; если станет общим, понадобится авторизация и разделение watchlist по пользователям.

## 5. Что делать не стоит

- **Оценивать рост звёзд по возрасту репозитория** (звёзды/день) и выдавать это за измеренный рост. Скрытые самоцветы так и сортируются, но подписываются как оценка.
- **Синхронизировать watchlist с сервером**, выдавая это за «облачный» список: это локальное хранилище, и так честнее.
- **Добавлять AI-описания репозиториев**: они будут выдумываться и смешиваться с реальными данными.
- **Ставить тяжёлые зависимости** (дашборд-фреймворки, ORM для локального JSON) ради косметики: на 4 ГБ RAM сборка уже занимает минуты.
